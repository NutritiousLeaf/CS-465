The Travlr Getaways project took a mix-and-match approach to frontend development. On one side, we had Express serving up HTML with Handlebars templates and JavaScript logic, on the other, an Angular single-page application (SPA). The Express side stuck to a classic Model-View-Controller (MVC) pattern every user request pinged the server, which responded with a freshly rendered web page. This structure made sense for the customer-facing site, giving us clear paths for routing and the flexibility to load up dynamic content through templates.

The Angular SPA was a different story, optimized for the admin dashboard. Instead of refreshing the entire page with every change, Angular’s SPA only updated what needed updating, right in the browser. Tasks like adding, editing, or deleting travel packages became much snappier. The component-based nature of Angular also helped keep the codebase tidy. We broke things down into modular chunks, making the code easier to manage and update as the project grew.

On the backend, we went with MongoDB, a NoSQL solution. Its flexible document format let us store travel packages and user data without the hassle of rigid tables or fiddly schema updates. That flexibility paid off as requirements changed, and because MongoDB works well with JavaScript, we kept a single language throughout the stack. This kind of consistency sped up development and cut down on the friction usually found in full stack projects.

JSON came up again and again as the glue holding everything together. While JavaScript is the actual language running the show, JSON just stores and sends data, it’s a format defined by key-value pairs, In our setup, JSON linked the Angular frontend, the Express server, and the MongoDB database. User actions in the browser sent JSON requests to the backend API, and the server responded in kind, passing back the data the frontend needed.As the project evolved, we kept refactoring major sections for clarity and speed. One big change, reorganizing trip display logic as Angular components. With this approach, we only had to build the code for a travel listing once, then reuse that same component wherever we needed it. This slashed code duplication, reduced errors, and made it simple to roll out updates. Streamlining API calls and trimming redundant code also made a difference in performance—less unnecessary reloading, more responsiveness.

Reusable interface components carried real advantages. We didn’t have to reinvent the wheel every time. One update in a component could ripple through a dozen places, saving time and effort. This also made it possible to scale the application without bogging down in rewrites or rewiring existing features.

Testing a full stack application means checking that every layer—frontend, backend, and everything between—plays nicely together. For APIs, we looked at individual endpoints, checked the request methods, and inspected what came back in response. GET requests pulled data (like travel packages), while POST and PUT let admins create or update them.

Once we added security, the testing challenge ramped up. We had to ensure our authentication worked, valid users could get in, everyone else got shut out. We tested both success and failure scenarios, confirming that unauthorized users couldn’t poke around or modify sensitive data. Browser dev tools and API testing suites like Postman helped here, letting us track requests, spot errors, and zero in on issues with JSON Web Token (JWT) authentication.Understanding how methods (like GET or POST), endpoints, and security measures work together is key. Methods spell out the action—are we fetching, updating, or deleting? Endpoints mark the URL where it all happens. Security locks down the sensitive routes. Together, these elements build the foundation of a robust full stack app.
